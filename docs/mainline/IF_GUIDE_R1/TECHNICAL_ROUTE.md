# InsightForge｜技术路线与实施计划
## IF-GUIDE-R1 · 在现有工作区实现行动与验收

**版本：1.0｜日期：2026-09-15｜对应规则：MAINLINE_RULES.md**  
**状态：拟实施设计；未检查当前实际仓库，未执行产品测试或部署。**

**目标：** 让用户从零证据想法开始，完成一项真实验证或第一条可用流程，并把实际结果返回 IF，用于下一步判断。

**架构：** 复用当前项目、账号、Snapshot、异步生成、文档与存储服务；新增轻量项目目的、行动任务、结果与复核对象。编程工具是外部执行端，IF 本期负责范围、交接、验收和结果解释，不默认代替 IDE 或运行环境。

**技术栈：** 2026-09-06 技术文档记录原生 HTML／CSS／JavaScript、FastAPI、Pydantic、httpx、按账号隔离的 SQLite 与进程内 worker [D2]。当前依赖版本以实际工作区为准，不迁移 React／Next.js，不重写认证与数据库。

### 实施原则
先在真实服务链上做一个最小端到端切片，再逐步扩展。可以使用现有计划执行与 TDD 工具，但无需安装额外方法论框架。本文的新增文件名与 API 是建议合同，接入时必须映射当前代码。

### 全局约束
普通用户不配置新 API Key；新增模型操作复用服务器配置，但必须显式注册，不能假定现有 solutions 操作支持所有任务。没有新模型调用时可用标明来源的规则模板；不能在生产缺凭据时悄悄 mock。

保留旧 PRD／TechDoc／Handoff、历史项目、用户选择、账号隔离、额度和幂等。新增低风险 coding 任务采用自己的清晰合同，不能通过削弱旧审批实现“零资料交接”。

### 交付顺序
M0 当前模块映射 → M1 项目目的与首次行动 → M2 最小流程及 coding 任务 → M3 结果回传与恢复 → M4 对照评测与受控试用。

## 1. 复用架构与模块职责

### 建议调用链
浏览器既有工作区 → 账号外层认证 → 用户 child app → 项目／行动服务 → 当前用户数据库与存储 → 既有异步生成服务或确定性模板 → 行动／任务产物 → 用户在外部执行 → 结果回传与复核。

任何新资源仍须验证当前账号与项目归属。不能接收客户端 `database_path`、`actor` 或 `workspace` 来决定权限。

| 历史技术线索 [D2] | 继续承担的职责 | 新增接入方式 |
|---|---|---|
| `app/main.py` | 服务构造、路由与生命周期 | 注册少量行动服务，不另造 app |
| `app/accounts.py`、`account_registry.py` | 认证、会话、用户工作区 | 沿用可信身份，不在新路由绕过 |
| `app/services/solution_design.py` | 方案生成与已有用户选择 | 按目的复用；不强制每次再生成方案 |
| `app/services/async_generation.py` | 意图、run 与终态 | 新 AI 操作显式接线；非 AI 模板不虚构 Provider attempt |
| `document_workspace.py`、`document_versions.py`、`handoff.py` | 文档、版本和正式交接 | 保留旧合同，新增轻量任务导出类型 |
| `source_guidance.py`、`sources.py` | 来源与证据分类 | 接收观察／结果，不自动升级真实性 |
| `app/static/index.html`、`app.js`、`styles.css` | 用户主工作区 | 增加当前行动卡、提交和恢复局部组件 |

### 建议新增逻辑单元
`project_intent` 管理项目目的与约束；`guided_actions` 管理验证和开发任务；`action_reviews` 检查提交结果；`task_pack_export` 组织安全任务包。优先作为现有服务文件的局部扩展；只有职责过重时才拆文件。

RAG 继续用于已经授权的项目资料。零资料场景不要求先建立向量库，不因新定位增加搜索供应商或外部爬虫。

## 2. 数据对象与兼容增量

### 最少四类逻辑增量

| 对象 | 最小字段 | 必须保持的语义 |
|---|---|---|
| ProjectIntent | project_id、purpose、confirmed_by、revision、目标、约束 | purpose 为 LEARNING／PERSONAL_USE／FOR_OTHERS／UNSPECIFIED；模型不能替用户确认 |
| ActionTask | task_id、project_id、kind、目标、输入、步骤、产物、检查、分支、snapshot_version、revision | 一次小任务；无 Snapshot 的首次行动允许为空，不强制先生成文档 |
| ActionSubmission | submission_id、task_id、task_revision、说明、附件引用、执行声明 | 保存用户实际提交，不与自动验收混为一谈 |
| ActionReview | review_id、submission_id、检查项、已知／未知、建议、确认记录 | 每个通过项有依据；未知不自动通过 |

模型名称是设计层名称，若现有表可安全表达则扩展，不建立同义表。任务模板可存版本化文件，首期不建模板管理后台。

### Task kind
`OBSERVE / MANUAL_TEST / LEARNING_EXERCISE / BUILD_SLICE / ACCEPTANCE / RECOVERY`。一个初次行动通常只属于一种；不能为了完整流程一次创建几十张任务卡。

### 产物事实分类
`USER_INPUT / MODEL_HYPOTHESIS / REAL_OBSERVATION / SIMULATION / IMPLEMENTATION_EVIDENCE`。保留既有 source_type 映射，不改变旧含义。`REAL_OBSERVATION` 表示用户声明并提供的真实观察记录，不等于平台已经独立验证其真实性。

### 任务与版本
行动任务创建后，用户可改目标、步骤与验收并生成新 revision。开发任务绑定已确认范围或 Snapshot；范围变更时旧任务仍可读，但结果应用前提示重评。初次行动不需要伪造 Snapshot 或文档批准记录。

### 附件
首期支持受限文本、JSON／CSV、截图等既有安全格式；不默认上传整个仓库、node_modules、模型文件或未脱敏数据库。附件归属绑定账号、项目、任务，不能通过 task_id 跨项目读取。

## 3. 状态机与任务路由

### 项目目的不是另一套长表单
用户只需确认“学习／自用／给别人使用”。已表达明确目的时预填但保留确认；不清楚时为 `UNSPECIFIED`，可以先做不会产生商业强主张的探索动作，不直接当成商业产品。

### 生命周期
`DRAFT → READY → IN_PROGRESS → SUBMITTED → CLOSED`；需要补充时为 `NEEDS_REVISION`，恢复后进入 `IN_PROGRESS`；暂停为 `PAUSED`。

单独保存 `decision = CONTINUE / NARROW / CHANGE / STOP / FINISH`。`CLOSED` 表示本轮处理结束，不等于代码通过、项目上线或市场成立；FINISH 必须对应本次明确目标的完成依据。

### 验收状态
逐项检查使用 `PASS / FAIL / UNKNOWN / NOT_APPLICABLE`。必需项出现 UNKNOWN 或 FAIL，不能给出“验收通过”；可保存部分成果并进入恢复任务。NOT_APPLICABLE 需要原因，不能用来隐藏失败。

复核层级 `USER_REPORTED / ARTIFACT_CHECKED / AUTHORIZED_RUN` 分开保存。本期系统不自动填写 AUTHORIZED_RUN；外部工具文字声明仍是提交材料，不是平台已运行。

### 确定性路由优先

| 条件 | 下一步候选 |
|---|---|
| 学习目的且目标能力明确 | 一个可以完成并解释的练习任务 |
| 自用目的且已有真实输入 | 一次现有做法与小原型对照 |
| 服务他人且没有行为材料 | 一次具体观察／手工测试，不要求完整调研 |
| 验证结果足以开始低风险开发 | 一条 BUILD_SLICE 任务及对应验收 |
| 缺少外部权限、敏感数据处理说明 | 先补授权或改用非敏感材料 |
| 开发产物已交回但关键行为失败 | 一条 RECOVERY 任务，不整项目重写 |

模型可以建议动作和解释，不能直接改变状态、写批准、提交用户决定或扩大权限。最终动作由用户确认，必要安全条件由服务器检查。

## 4. 首次行动与最小开发任务合同

### 首次行动卡
必须包含：你正在验证什么；为什么现在做；拿什么材料；具体怎样做；交回什么；怎样检查；不同结果说明什么；可以什么时候停下。页面正文尽量用普通中文，后台使用结构化字段。

示例：用最近三条课程通知，记录现有整理方式，再手工提取事项与日期。产物是原文、现有处理方式和遗漏点，不是模型生成的“模拟访谈”。这是一项诊断动作，不声称样本代表全部学生。

### 最小 coding 任务包

| 部分 | 必需内容 |
|---|---|
| 本轮范围 | 一个用户流程、输入输出、当前目的 |
| 保留项 | 不能改变的旧路由、数据、权限、现有行为 |
| 明确不做 | 暂不实现的账号功能、支付、批量抓取等按项目列出 |
| 技术输入 | 已核实仓库事实；没有仓库材料时只提供需求级建议 |
| 实施任务 | 先确认依赖，新增最少代码，写相关测试，运行并返回事实 |
| 用户验收 | 正常、缺失、重复、修改、失败恢复的具体操作 |
| 结果回传 | 改动范围、执行命令、结果、失败、限制与关键截图／日志 |
| 权限与风险 | 明确外联、写库、发布、删除等是否获准 |

### 双重交接类型
`PROTOTYPE_TASK`：经过任务范围、风险、输入和用户确认的低风险实验／开发任务，不强制依赖整份 PRD。

`FORMAL_HANDOFF`：继续执行当前正式 PRD／TechDoc、版本和健康状态合同。不能将前者转换为后者的“批准证明”。两种类型在页面、导出头部和 API 中明确标识。

### 外部编程工具
首期导出 Markdown＋结构化 JSON，可由用户交给现有工具执行；不自动建立 GitHub 写权限、远程 MCP、仓库部署或终端执行链。发现真实重复交接需求后，再单独论证集成。

导出内容只带当前任务所需资料，排除密钥、账号会话、数据库路径、无关私人信息和未授权原文。导出完成不会自动关闭开发任务。

## 5. 结果回传、卡点恢复与模型接入

### “我做完了”
用户选择本轮任务，填写执行环境与实际结果，上传必要产物，并逐项填写检查。系统先验证归属、版本、格式和必需项，再给出材料检查与下一步候选。

不得只接受“AI 说所有测试通过”作为全部验收依据。可请求相关测试输出与实际用户流程记录；仍无法核实时保留 UNKNOWN，而不是伪装独立运行。

### “我卡住了”
最少收集：卡在哪一步、做了什么、预期是什么、实际发生什么，以及安全脱敏的错误信息。分类为环境／需求不明／实现缺陷／数据问题／服务故障／验收不清。

优先给一个最小恢复动作，例如“先确认保存后的记录是否真的写入，再检查刷新时读取”，而不是重新生成全套架构。确实需要查看仓库时提出最小材料范围，不索取整库秘密。

### 三个首发模板
首次行为观察；第一条可用流程；失败定位与验收恢复。每个模板包含 inputs、outputs、checks、branches、prohibited_actions 和版本。先用受控规则模板验证用户任务，再按必要性增加模型自由生成。

### 新模型操作必须显式注册
历史文档只明确 managed router 的 `solutions` 操作 [D2]。新增 `guided_action`、`build_task`、`result_review` 若需要模型，必须逐个接入当前服务端注册与 schema、预算、权限和测试；不能从“能选模型”推断这些操作已经可调用。

模型输出包含简短依据和真实来源引用，不要求展示隐藏思维过程。非法字段、假引用、过大任务、未经授权操作和无依据“已通过”都由确定性 validator 拒绝。

### 可用性降级
模型不可用时已有任务和提交可读写，规则模板仍可使用且明确标注；动态生成失败保留输入与状态。用户明确选择重新生成或换模型才创建新意图，不自动切模型掩盖失败。

## 6. API、并发、幂等与执行事实

### 拟新增接口
下列是建议语义，实际前缀及 DTO 需在 M0 与当前服务对齐；已有等价接口直接复用。

| 方法与路径 | 输入／输出 | 约束 |
|---|---|---|
| PUT `/api/projects/{p}/intent` | purpose、目标、expected_revision | 用户确认；旧版本冲突为 409 |
| POST `/api/projects/{p}/actions/propose` | 目的、输入、任务类型、意图键 | 规则模板可直接建草稿；模型生成走既有 run |
| GET `/api/projects/{p}/actions/{t}` | 任务、状态、allowed_actions | 服务端决定归属和可做动作 |
| PATCH `.../actions/{t}` | 用户修改、expected_revision | 保存新 revision，不覆盖他人／旧标签页内容 |
| POST `.../actions/{t}/confirm` | 明确确认、expected_revision | 任务资格检查，不写旧文档 approved |
| POST `.../actions/{t}/export` | PROTOTYPE_TASK 或正式合同入口 | 检查类型、版本与权限，导出不等于执行 |
| POST `.../actions/{t}/submissions` | 结果、附件 ID、任务版本 | 幂等提交，不重复创建复核 |
| POST `.../submissions/{s}/review` | 复核请求、意图键 | 规则与模型结果分开，记录未核实项 |
| POST `.../actions/{t}/decision` | 继续／缩小／调整／结束 | 用户确认；结果上下文必须仍适用 |

任务查询和模型 run 查询复用既有模式，POST 返回 202 只代表接收。不要把轮询、页面返回和任务查看写成新生成操作。

### 唯一约束
幂等键绑定可信账号、项目、操作与用户意图；同键不同参数返回冲突。每个真实模型意图最多一次获准派发；事务记录与外部派发之间的崩溃可能造成远端结果未知，不能宣称分布式“恰好一次”。

已有 run、reservation、attempt 的实际字段语义以当前服务为准，不因新界面统一名字而改变计费事实。任务生成、结果检查、再次生成是不同操作，不能共用同一成功结果。

### 并发与恢复
新增任务采用 expected_revision 条件写入，不能把文档已有 base-version 校验当作完整多标签页防覆盖。中断后恢复原 task／run；已派发而结果未知时不自动重发。取消本地等待不证明远端模型停止或不再收费 [D2]。

## 7. 成本、安全与部署约束

### 成本控制
新的模型操作默认每意图最多一次派发，不自动模型级联。规则模板不登记为真实 Provider 请求。operator 成本与用户成功使用额度分开；应用失败或用户额度释放不能抹掉上游已发生费用。

新功能开关默认对正式用户关闭，测试新操作默认阻断外联；这不修改已获准上线的既有生成策略。真实试验前限定模型、环境、次数与预算。价格未知记录未知，不填写 0。

### 不可信材料
截图、日志、CSV／JSON 和代码说明都不能携带系统指令权限。限制上传大小与解压体积，净化展示内容，禁止执行脚本和不安全反序列化。对代码中的命令只作为待审查文字，不自动执行。

任务包明确提醒不要粘贴 API Key、访问令牌、完整数据库、敏感客户资料。服务器仍需做类型、大小、归属和秘密暴露检查；仅靠提示不能完成保护。

### 账号和数据
新对象进入当前用户 child DB／合法存储范围。所有 GET、导出、提交、确认和删除分别验证归属，不能只保护列表。切换账号清理当前页面状态，不清除其他用户真实数据。

私有附件默认不公开。删除任务或项目的传播应遵循已有保留／删除策略，派生缓存不得继续泄露内容。技术日志记录安全状态与计数，不默认保存完整用户想法、提示和响应。

### 运行与部署
保持当前已认可的服务拓扑和持久化位置。2026-09-06 文档的并发验证范围为单进程 [D2]，本期不能直接增加多个独立 worker 并声称任务协调已保证；当前若已有更新证据则按实际情况适配。

进程内任务的恢复与外部调用事实是首要可靠性问题，不以部署更多服务代替。只有真实瓶颈与测试表明需要时，才提出独立执行器或存储调整；不把框架升级设为主线前置。

## 8. 迁移与界面调整

### 兼容迁移
给历史项目新增 purpose 时默认 UNSPECIFIED，不推断商业目的。旧项目打开后仍能使用方案、Snapshot、文档和历史功能；引导仅在用户启用或需要时接入。

新增表／字段先在副本验证 additive 迁移；保留项目 ID、文档版本、审批与额度记录。新旧写入者不能未知地同时操作同一库。备份与恢复验证针对实际受影响数据，不做全项目形式化对账。

### 旧正式 Handoff 兼容
正式交接继续使用现有批准版本与健康检查。低风险任务包采用独立类型与检查，UI 不显示“正式交接已通过”。项目无完整资料时不得通过伪造文档、删除 validator 或写数据库批准字段来放行。

### 页面增量
在现有首页增加目的选择和当前行动，不把全部导航改成新系统。保留方案详情关闭、历史项目、草稿、文档编辑、版本差异、模型设置与原有错误恢复。

当前任务页默认突出目标、动作、产物和验收，来源与技术细节可展开。必要澄清一次聚焦一件事；用户已经明确的信息不重复询问。示例一键填入前标明演示，不自动当作真实反馈。

### 真实状态与无障碍
主按钮由后端允许动作驱动；状态至少解释生成中、等待用户、提交失败、需补充和已结束。没有真实进度不伪造百分比。键盘可达、弹层可关闭，移动端与桌面缩放不遮挡主按钮。

刷新与重登恢复原任务，未保存内容不得被错误状态静默清空。409 时保留本地修改并提供比较／重载，不悄悄覆盖。关闭新功能开关后，旧入口保持可用，新增记录不删除。

### 范围变更传播
目的、Snapshot 或任务范围发生变化时，相关新任务标为需重评；旧文档不自动改写。用户确认新任务范围后生成新版本，不能把历史结果直接当作新范围的验收。

## 9. 必须实现的验收用例

下表是设计合同，不是已执行测试结果。需要真实服务链、数据库状态和浏览器观察共同验证。

| ID | 场景与操作 | 预期结果 |
|---|---|---|
| IF-T01 | 零资料项目选择学习目的 | 可以生成并保存练习行动；不要求市场证据 |

## 10. 分阶段开发工单

### M0｜当前模块映射
读取 AGENTS.md、当前启动链、依赖和相关服务；保护工作树未提交修改。运行本轮相关基线测试，输出一页 `WORKSPACE_MAP.md`：现有入口、等价功能、受影响文件、实际测试命令和阻塞。随后进入 M1，不展开全库重构或治理盘点。

### M1｜零资料也能开始行动
**输入：** 当前项目、IdeaBrief 或一句 idea、用户目的。**输出：** 一张可修改、保存和恢复的行动卡。

- [ ] 写 IF-T01 至 T05、T16 的失败测试，覆盖三个目的与零资料。
- [ ] 复用项目和用户存储，接入目的与行动模型，先用受控规则模板。
- [ ] 在既有首页接入目的与当前行动，不要求先创建正式 Snapshot。
- [ ] 完成保存、重新打开、换账号与浏览器路径；跑相关旧行为回归。

**停止点：** M1 完成后提交事实回执，不继续自动实现全部路线。

### M2｜第一条可用流程与任务交接
**输入：** 目的、已获得的结果或明确假设、当前范围。**输出：** 一个经过用户确认的最小 coding 任务包。

- [ ] 写 IF-T06 至 T10，覆盖新旧交接与明确未知。
- [ ] 实现任务范围、必需检查、两个导出类型和脱敏导出。
- [ ] 用课程通知示例验证正常、模糊时间、重复与保存恢复。
- [ ] 检查其他领域例子，不能把通知工具写成所有用户默认模板。

### M3｜结果复核与卡点恢复
**输入：** 任务版本、结果与检查记录。**输出：** 逐项复核、未核实项与一个后续动作。

- [ ] 写 IF-T11 至 T18；重点验证越权、未知结果、重放和并发。
- [ ] 接入结果提交、检查状态、用户决策；模型操作逐项注册并受既有运行合同约束。
- [ ] 完成“我做完了／我卡住了”真实浏览器路径。

### M4｜评测与受控试用
执行 IF-T19／T20 及相关全链回归。对照通用 AI＋清晰提示、静态模板、IF 状态化引导，记录全部启动用户、不同目的、失败及支持成本。未形成净收益则减小范围，不增加 Agent 数量作为补救。

## 11. 效果评测、发布与开发回执

### 工程与价值分开
工程要求身份、数据、幂等、状态、版本、错误恢复和导出安全正确。产品要求用户实际完成动作并能理解结果。一个层面通过不能替代另一个层面。

评价任务卡时检查：目标是否匹配目的；动作是否具体且资源可得；是否提供可检查产物；验收能否发现错误；下一步是否依据结果改变；是否存在虚构证据或越权建议。

静态模板、通用 AI 与 IF 的对照应使用相似资源和任务条件。若只在 IF 中提供更多帮助材料，不能把全部效果解释为状态化引导。探索测试先确定观察窗口与分母；正式比较的阈值和成本边界应在看结果前确定。

### 生产级但不过度建设
上线前验证当前适用环境的真实持久化、重启恢复、身份隔离和完整用户路径。真实模型验收限制次数与预算；本地规则模式通过不代表真实模型操作已通过。

发布分层记录：本地组件、服务集成、浏览器、真实模型、目标环境、用户试用。只在对应证据存在时声明完成。无需等待不存在的全项目 authority root 才开展正常开发。

### 本轮开发回执模板
```text
work_item: IF-GUIDE-R1/M1
changed_files: 实际文件与修改目的
rules_covered: IF-01, IF-02, IF-04, IF-11
tests: 实际命令、结果、环境与未运行项
external_access: none 或实际授权及调用次数
migration_and_cache: 实际变更与失效范围
product_path: 实际用户操作及可见结果
known_limits: 仍未支持／未核验事项
next_task: 一个最小后续任务
```
字段说明不是结果；提交时填写事实。用户目标完成、决定暂停和开发通过分别记录，不能通过更改“成功”含义提高指标。
