# InsightForge｜主线规则
## IF-GUIDE-R1 · Idea 验证与第一条可用流程

**文档版本：1.0｜日期：2026-09-15｜适用：InsightForge 独立工作区**  
**性质：已确认方向的开发约束；不是代码完成或部署验收报告。**

> 核心定位：帮助会使用 AI 工具、但不会拆解任务和验收结果的学生、转岗者及早期实践者，从一个想法出发，以最低必要投入完成有效验证或第一条真正可用的流程。

### 本轮唯一主线
Idea／真实问题／半成品 → 明确本次目的 → 一个低成本判断动作 → 收敛一个最小可用流程 → 一轮 AI coding 任务 → 用户验收与结果回传 → 继续、缩小、调整或结束。

**PRD、技术说明和作品集材料继续保留，但成为真实决策与结果的派生产物，而不是主线完成标准。** 不要求所有项目商业化，不为了留存强造复用循环，也不承诺一个想法自动变成成熟产品。

### 这套规则如何使用
先读本文件，再读 `TECHNICAL_ROUTE.md`，最后使用 `CODEX_START.md` 启动首轮开发。`WORKSPACE_RULES_APPEND.md` 只追加规则，不覆盖 AGENTS.md。完整依据见 `SOURCES.md`。

| 信息类别 | 本文采用的口径 |
|---|---|
| 用户确认方向 | 本次对话已同意的引导式主线 [U1] |
| 既有产品设计 | 2026-09-03 PRD 的 Quick Value、IdeaBrief、Snapshot 和渐进式证据 [D1] |
| 既有技术线索 | 2026-09-06 TechDoc 的原生网页、FastAPI、账号工作区与异步生成 [D2] |
| 当前实现与部署 | 本次未直接检查真实工作区；不得用旧文档断言现状 |
| 新增流程、接口、验收 | 本套方案提出的设计，均需要接入与验证 |

### 首轮完成的用户价值
一个没有调研材料的用户，也能根据学习、自用或服务他人的目的，拿到并保存一张具体的首次行动卡；操作、产物和完成标准清楚，刷新后可以继续。不要求首轮同时建成代码执行平台或完整商业化链路。

## 1. 不可退让的主线规则

| 规则 | 必须遵守的行为 |
|---|---|
| IF-01 目的先于流程 | 学习、自用、服务他人分别定义成功；未知目的先保留未确认，不默认商业化。 |
| IF-02 零证据可以开始 | 不把调研报告、来源库或付费意愿证明设为低风险探索前置。 |
| IF-03 验证不是找支持 | 帮用户寻找能判断是否继续的信息，允许反证和暂停，不替 idea 找借口。 |
| IF-04 一次只推进一小步 | 优先一个低成本动作或一条可用流程，不默认全产品蓝图。 |
| IF-05 非 AI 方案可成立 | 手工、表格和低自动化方案可能足够；不强迫每个项目使用 AI。 |
| IF-06 代码生成不是完成 | 生成计划、导出交接包、AI 声称完成都不等于运行、通过测试或上线。 |
| IF-07 验收用户能做 | 描述操作、输入、应看到什么和失败怎么办，不能只写“功能正常”。 |
| IF-08 结果改变下一步 | 引导必须消费实际结果；不能只让用户勾选完成后解锁更多模板。 |
| IF-09 来源身份不升级 | AI 推断、用户确认、真实观察、模拟材料和运行证据不可互相替代。 |
| IF-10 低风险可逆推进 | 不确定时缩小动作；真实隐私、付费、公开发布和不可逆操作仍需要适用检查。 |
| IF-11 保留兼容与可靠性 | 不回退账号隔离、生成幂等、额度结算、文档版本、历史中心和失败恢复。 |
| IF-12 不强造复购 | 完成项目或有依据地结束可以是成功，不把所有退出认定为流失失败。 |

### 不进入本期
不做新的通用 AI 编程 IDE、任意仓库自动执行、无人值守自动部署、项目社区、技能市场、复杂多 Agent 编排、企业协作平台或支付订阅系统。暂不迁移前端框架。

这些是范围控制，不是“按玩具 Demo 开发”。新增能力必须接入真实业务链，覆盖存储、权限、失败和恢复；只是把每轮承担的用户任务控制在合理范围。

## 2. 三种目的与渐进式证据

| 目的 | 先验证什么 | 第一份合格材料 | 暂不要求 |
|---|---|---|---|
| 学习 `LEARNING` | 是否能掌握目标能力并解释实现 | 一次练习产物、自己的解释和检查结果 | 市场规模、商业转化、访谈数量 |
| 自用 `PERSONAL_USE` | 是否比自己当前办法更有效 | 一个真实任务的前后对照或使用记录 | 需求必须普遍存在 |
| 服务他人 `FOR_OTHERS` | 目标用户是否遇到问题，现有办法哪里不足 | 一次具体行为观察、手工测试或原型反馈 | 大量调研、完整商业计划 |

用户可以改变目的，系统保留原记录并重评后续任务。已有项目不擅自回填目的；先显示未确认，只在需要时提出一次简短选择。

### 初次动作不要写成“请上传证据”
例如用户想做课程通知整理工具，可先让他拿出最近实际处理的几条通知，记录原来怎么提取事项、怎样记截止时间、哪里发生遗漏。做给别人时，可以请一位近期处理过通知的同学演示真实过程；不要只问“你喜不喜欢这个 idea”。

少量观察只提供探索线索，不能自动变成“需求已被市场验证”。模拟访谈可作练习，必须标为模拟，不进入真实用户研究统计。

### 可以带着不确定性前进的动作
手工整理、纸面原型、一次受限输入输出测试和可丢弃的小原型，可以在明确假设与风险后开展。不需要为了生成行动卡先补齐 PRD、资料库或 Canvas 全部字段。

### 需要先停下来核对的动作
处理真实敏感数据、公开发布、支付、不可逆删除、对第三方发消息、长期投入昂贵服务，需要与风险匹配的授权和检查。未知不等于禁止一切，但也不能以“新手友好”为理由绕过安全。

### 既有设计如何延续
旧 PRD 已经允许无证据探索，并强调 AI 提议、用户确认和假设披露 [D1]。本轮新增重点是让用户以具体行动获得新信息，不是把“允许跳过证据”再做一遍。

## 3. 核心流程与第一条可用链

### 用户看到的流程
“我现在想完成什么” → “先做这件小事” → “把结果交回来” → “只做最必要的一条流程” → “交给编程工具执行本轮任务” → “按步骤检查” → “继续或结束”。

首页默认展示当前任务及最重要的下一步。完整路线可展开，术语按需解释；不让初学者先学习 RAG、MCP、状态机或资料真实性枚举。

### 课程通知工具的示例范围
第一版只处理：粘贴通知 → 提取事项与截止时间 → 展示原句 → 用户确认或修改 → 保存并重新打开。

账号、多人协作、自动抓取、支付和复杂提醒是否进入后续版本，取决于当前用户目的与验证结果。应用本身的权限和数据安全仍然要满足真实使用边界。

### AI coding 任务包必须包含
本轮目标；输入与依赖；明确不做的事；不能改变的已有行为；具体实现范围；用户可执行的验收步骤；异常与恢复；需要返回的运行结果；已知假设与风险。

**不得只导出“请把整个产品做出来”。** 不了解用户实际仓库时写清需要检查的模块与条件，不捏造存在的文件、命令或成功测试。

### 新任务包与旧正式 Handoff 分开
保留现有 PRD／TechDoc 审批与正式 Handoff 约束 [D2]。新建的低风险原型任务可以采用独立的“本轮任务确认”合同，不强制先生成整套文档；不能靠删除旧 validator、伪造 approved 或把不健康文档直接标健康来实现。

### 两个必需返回入口
“我做完了”接收实际产物与检查记录；“我卡住了”接收失败步骤、输入、预期和实际结果。系统先判断环境、需求、实现或验收问题，再给一个最小恢复动作，而不是重新生成整个项目。

## 4. 验收、反馈与决策规则

### 验收写成用户能照做的步骤

| 场景 | 用户操作 | 需要观察的结果 |
|---|---|---|
| 正常流程 | 输入一条有明确日期的通知，确认后保存 | 事项与日期正确，原文可回查，刷新仍存在 |
| 时间不明确 | 输入“下周五交作业”，不提供通知发布时间 | 请求必要信息或保留待确认，不能私自编造确定日期 |
| 重复操作 | 连续点击保存，或刷新后回到任务 | 不产生非预期重复记录／重复生成调用 |
| 修改结果 | 改正提取错误后保存并重新打开 | 展示修改后的内容，而不是旧模型结果 |
| 服务失败 | 模拟模型或网络失败 | 输入保留，失败可理解，有明确恢复路径 |

### 结果不等于好评
“用户说不错”不等于真的愿意使用；“代码测试通过”不等于解决了需求；“能够部署”不等于已公开上线。反馈记录应说明发生了什么、在哪里观察到，以及能够支持多大范围的判断。

### 决策分支
**继续：** 当前动作提供了足够依据，进入下一小步。  
**缩小：** 需求或实现超出资源，保留最有价值的部分。  
**调整：** 结果否定当前解释，修改目标或方案。  
**结束／暂停：** 目标已完成，或当前不值得投入；保留原因和产物。

关键选择由用户确认。系统可推荐，但不能为了流程完成率自动替用户选方案、确认文档、声称验收通过或继续扣费。

### 三种事实层级
用户报告完成；系统检查了提交材料；在明确授权环境中独立运行。三者分别显示。本期以任务包和结果检查为主，不能把未提供的执行通道写成已经验证。

### 保护已有可靠性合同
沿用真实账号与项目归属、服务端模型注册、意图／任务幂等、状态恢复和费用记录。新增任务不能因页面重入自动调用 Provider；远端结果不明时不盲目重发。成功使用额度与服务方实际费用仍分开 [D1][D2]。

## 5. 范围取舍与开发里程碑

| 处理方式 | 本期安排 |
|---|---|
| 保留复用 | IdeaBrief、必要澄清、方案比较、用户选择、Snapshot、文档编辑／版本、历史中心、模型运行与账号隔离。 |
| 优先新增 | 目的识别、首次行动卡、最小流程范围、本轮 coding 任务、验收与卡点回传。 |
| 调整主位置 | PRD 不再是默认终点；证据不再只是上传资料，而是验证动作产生的结果。 |
| 延后验证 | 半成品救援的深度仓库能力、跨工具自动接入、完整项目课程、订阅商业化。 |

### 五个里程碑
**M0 接入与映射：** 核对当前相关服务与测试，明确哪些能力已有，保留未提交工作，不重构框架。

**M1 零证据首次行动：** 用户确认本次目的后，得到一张具体行动卡，能够修改、保存和恢复。优先采用受控模板接入真实业务链，不要求新增联网搜索。

**M2 第一条可用流程：** 根据当前目的与结果生成小范围任务包；本轮任务审批与旧正式 Handoff 分开。

**M3 结果回传与卡点恢复：** 用户提交验收结果，系统按实际材料提出继续、缩小、调整或暂停。

**M4 效果验证与受控试用：** 比较静态模板、通用 AI 和状态化引导，决定是否继续扩大能力。

每个里程碑均含相关权限、版本、幂等与浏览器回归，不在最后一轮才补安全。已经实现的部分以当轮测试验证后复用，不重复做。

### 首轮明确停止点
完成 M0 与 M1 的端到端切片后报告；不同时扩成代码执行平台、竞品爬虫、支付或新前端。缺少新模型能力时使用明确标注的规则模板，不能把 mock 混入生产生成结果。

### 关于“项目结束”
结束不自动算失败，也不自动算成功。学习目标完成、真实任务改善、得到有依据的否定结果分别记录。无产物且无理由的退出单列，不用“有价值的暂停”包装普通流失。

## 6. 指标与失败退出条件

| 指标 | 定义与注意事项 |
|---|---|
| 首次有效行动率 | 在预先约定时间内完成一个可检查动作的项目／全部启动项目；按目的分组。 |
| 首条可用流程完成率 | 实际完成最小用户流程并通过对应验收的项目／进入该开发任务的项目；另报总体转化。 |
| 独立验收率 | 用户不依赖额外代操作即可按步骤发现通过／失败的任务比例；需包含故意植入的错误案例。 |
| 有依据决策率 | 有可核查产物或合理分析支撑继续／缩小／调整／结束的项目比例；不等于商业需求验证率。 |
| 卡点恢复率 | 从已记录阻塞恢复到可继续动作的任务／全部提交阻塞任务；未解决项不得剔除。 |
| 严重错误与成本 | 越权、重复派发、伪造证据、错误宣称已执行；费用与人工支持计入失败尝试。 |

### 验证设计
先用 8—12 名真实目标用户做探索性任务观察，带自己的想法或半成品，覆盖学习、自用和服务他人。小样本用于发现阻塞，不作为市场留存、付费或效果显著性的证明。

对照通用 AI＋清晰提示、静态行动／验收模板，以及 IF 状态化引导。控制模型能力、时间预算、项目难度和材料条件；同时测第一份产物与用户能否解释取舍。技术故障计入总体结果，再单独归因。

若教学价值进入主张，应另给一个类似任务，减少提示后测试独立推进。仅在助手全程带领下完成一次，不能证明学会了方法。

### 成功标准
阻断性工程用例全部通过；用户能得到具体动作、真实提交结果并据此改变下一步。正式量化差异、成本和可接受退化在试验前确定，不看完结果再改门槛。

### 退出条件
若用户只复制计划却无法执行，先缩小任务而非增加模型；若静态模板已经同样有效，撤回额外调度复杂度；若定位用户只需要即时生成页面，应重新评估人群而非强迫使用方法论流程。

IF 可以是阶段性任务产品。按项目或阶段收费仅为后续商业假设，不为验证新主线而立刻建设支付、订阅或强制复购机制。

## 7. 工作区执行与主张边界

### 增量开发
2026-09-06 TechDoc 记录原生 HTML／CSS／JavaScript、FastAPI、按账号工作区隔离的 SQLite 和既有异步 worker [D2]。本轮沿用这一结构；实际仓库若已变化，记录并适配，不根据旧资料回退。

现有账号与会话、用户数据、生成 run、费用记录、Snapshot、文档与审批历史不得清零。新增字段兼容默认，历史项目目的未确认，旧文档不自动成为新任务的完成证据。

不主动加入全项目 SHA256 对账、形式化 authority、membership、复杂证据审批或重复盘点。局部版本、必要缓存键、输入摘要和实际测试足以支持本轮开发追踪；身份隔离与幂等不得因此放松。

### 外部边界
本次方向批准不等于授权购买服务、发送用户资料给任意外部模型、访问代码仓库写入、执行上传脚本、线上迁移或公开部署。新增真实调用须有明确环境、次数与预算；原有有效能力不因新功能开关被误关闭。

工作区存在生产冻结时继续遵守；获准本地开发与真实发布分开。只阻塞有依赖的环节，不以历史治理缺口阻断所有新功能开发。

### 开发回执
报告修改文件与目的、覆盖的规则、实际测试及未运行项、外联与费用、迁移／缓存影响、已完成用户路径、剩余风险和下一项最小工作。不要把测试数量、HTTP 202 或导出包当作产品有效性的替代。

### 可以说与不能说
经过实际验收后，可以说“帮助新手拆解验证动作、组织开发任务并检查提交结果”。不能说“已证明市场需求”“自动开发并上线完整产品”“完成真实用户闭环”或“独立验证代码”，除非相应事实确实发生且边界明确。
